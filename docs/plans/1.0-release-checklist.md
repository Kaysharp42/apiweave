# APIWeave 1.0.0 Release Checklist

*Internal manual checklist for the 1.0.0 cut. It covers the checks CI cannot
perform: real installs on clean machines, upgrading a 0.22.0 data directory,
rehearsing the update and rollback paths, and the first signed build. It is not a
public contract, and a checked box is not a substitute for the release
workflow's own gates.*

## Before the Tag

- [ ] The release commit is on `main` and `app/package.json` and
      `app/package-lock.json` both say `1.0.0`.
- [ ] `CHANGELOG.md` has the `## [1.0.0] — 2026-11-09` entry and no unreleased
      items left behind.
- [ ] [Known limitations](../reference/known-limitations.md) still match the
      release candidate.
- [ ] `npm run typecheck`, `npm run lint`, `npm test` and `npm run build:app`
      pass on the release commit; the CI quality gate is green on that commit.
- [ ] `git tag --list v1.0.0` is empty locally and
      `git ls-remote --tags origin v1.0.0` is empty on the remote.
- [ ] `UPDATE_SIGNING_PRIVATE_KEY` exists and matches
      `app/electron/update_signing_key.ts`. Configure the platform signing
      secrets in [Code Signing and Notarization](#code-signing-and-notarization)
      if this release should be signed.
- [ ] The `release` environment exists with a required reviewer, and
      `desktop-release.yml`'s publish job is allowed to use it. Do not approve
      that job until every check below passes against the draft.

## Draft Release Candidate

Pushing the tag starts the workflow. The build and CLI jobs fill a **draft**
release; the publish job then waits for the `release` environment's reviewer.
Nothing is public and `/releases/latest` still points at 0.22.0 while the draft
waits.

- [ ] Push the tag only after the release commit is on `main`.
- [ ] The workflow reaches the `publish` job and waits for approval.
- [ ] Download the candidate artifacts from the draft and run the clean-machine
      matrix, the 0.22.0 upgrade, the update rehearsal and the rollback drill
      below. Use a locally generated checksum if the draft's
      `SHA256SUMS.txt` is not final yet.
- [ ] Do not approve the publish job until every row and box passes. If a check
      fails, cancel the workflow; the cleanup job removes the draft. Fix the
      commit and push a new tag rather than editing a published release.

## Clean-Machine Install Matrix

Use a fresh VM or snapshot per row, with no previous APIWeave install or data
directory. Download from the draft release or the candidate artifacts, and
verify each download against the published `SHA256SUMS.txt`, or a locally
generated checksum for a pre-release candidate.

| Platform | Candidate artifacts | What to prove |
| --- | --- | --- |
| Windows 10 22H2 x64 | `APIWeave-1.0.0-win-x64.zip` (installer inside), `.msi` | Per-user install without admin, Start-menu entry, launch, uninstall |
| Windows 11 x64 | same | Same, on the current Windows release |
| macOS 13 Ventura | `mac-x64.dmg` and `mac-arm64.dmg` as hardware allows | Drag to Applications, launch, Gatekeeper behaviour |
| macOS 14 Sonoma | same | Same |
| macOS 15 Sequoia | same | Same |
| Ubuntu 22.04 x64 | `.deb` and `.AppImage` | `apt install`, launch, AppImage FUSE path |
| Ubuntu 24.04 x64 | same | Same |
| Fedora (current) x64 | `.rpm` | `dnf install`, launch |
| Arch (current) x64 | `.pacman` and `.AppImage` | `pacman -U`, launch, no FUSE dependency for `.pacman` |

For each install:

- [ ] The SHA-256 matches `SHA256SUMS.txt`.
- [ ] The app opens at the workflows list and **Settings → Updates** shows
      `1.0.0`.
- [ ] `<userData>/apiweave.db` and `<userData>/keyfile.json` are created.
- [ ] A small workflow with an HTTP request and an assertion runs and passes
      (use a local echo server if there is no external endpoint).
- [ ] Quit and relaunch: the workspace, workflow and run history are still
      there.
- [ ] A signed and notarized macOS build opens without a Gatekeeper workaround,
      and a signed Windows build shows a verified publisher. An unsigned
      candidate shows the documented warning and still opens after
      **More info → Run anyway** / right-click **Open**.
- [ ] Windows uninstall completes; note whether the data directory remains.
- [ ] On Linux, the package manager records the package, and the AppImage runs
      both normally and with `--appimage-extract-and-run`.

## 0.22.0 to 1.0.0 Upgrade

1. On a clean VM, install `v0.22.0` from its release.
2. Create a workspace, project and workflow with an HTTP request, an assertion,
   an environment variable and a secret. Run it once.
3. Track the workspace in git, connect a test remote, and note the run history
   and MCP token (enable the bridge once).
4. Install `1.0.0` over the existing install.

- [ ] The app opens without a startup error and shows `1.0.0`.
- [ ] `<userData>/backups/apiweave-*-v*.db` holds the pre-upgrade copy.
- [ ] The workspace, project, workflow, environment variable, secret and run
      history are intact.
- [ ] A run still resolves the secret and passes.
- [ ] Git sync still works; the next commit upgrades
      `.apiweave/format.json` to version 2.
- [ ] A pre-1.0 repository (`format.version` 1) opens, reads its environments
      with every environment extending none and no presets, and writes version 2
      on its first commit.
- [ ] The MCP bridge still starts with the existing token, or the token can be
      regenerated and the client reconnected.
- [ ] A JUnit and an HTML report still export from History.
- [ ] Repeat the install-over test on at least Windows and macOS. On Linux,
      upgrade the same package type (`dpkg -i`, `rpm -U`, or `pacman -U`).

## Update Rehearsal on the Throwaway Repo

Follow [Rehearsing the update path](../reference/release-and-updates.md#rehearsing-the-update-path-before-users-run-it).
Use a throwaway public repository with its own update signing key, never the
production repository.

- [ ] The throwaway repo has the release workflow, its own publish URL and its
      own `UPDATE_SIGNING_PRIVATE_KEY`.
- [ ] `0.0.1` is published and installed for real on Windows, macOS and Linux
      AppImage.
- [ ] `0.0.2` is published; the installed `0.0.1` notices it, downloads it,
      verifies the signature, installs on restart and reports `0.0.2`.
- [ ] The macOS `latest-mac.yml` lists both architecture zips, and each
      architecture verifies its own per-file signature.
- [ ] An unsigned macOS build follows the notice-only path and does not
      self-install.
- [ ] `.deb`, `.rpm` and `.pacman` show the `version.json` notice and do not
      self-install.
- [ ] The log records the provider request, the resolved file, the sha512 result
      and the signature result.
- [ ] Optional for iteration: `APIWEAVE_DEV_UPDATES=1 npm run dev` reaches the
      same repo through `app/dev-app-update.yml`.

## Rollback Drill

Run this on the throwaway repo before it is needed on a real release.

- [ ] Publish a deliberately bad `0.0.3`, then run the **Update rollout**
      workflow with `percentage: 0`. Confirm the manifests keep their
      `version`, `path`, `sha512` and `apiweaveSignature`, and clients stop
      being offered the update.
- [ ] Mark `0.0.3` as a prerelease. Confirm
      `/releases/latest/download/version.json`, `latest.yml`,
      `latest-linux.yml` and `latest-mac.yml` resolve to `0.0.2`.
- [ ] Confirm a machine already on `0.0.3` is not downgraded; it waits for a
      higher version.
- [ ] Publish `0.0.4` and confirm `0.0.3` updates forward.
- [ ] Restore the throwaway repo to a clean state and record the commands and
      results.

## Code Signing and Notarization

- [ ] The update-signing private key is set as `UPDATE_SIGNING_PRIVATE_KEY`,
      its public half is committed, and an offline backup exists.
- [ ] macOS: `CSC_LINK`, `CSC_KEY_PASSWORD`, `APPLE_ID`,
      `APPLE_APP_SPECIFIC_PASSWORD` and `APPLE_TEAM_ID` are set. Without the
      `APPLE_*` secrets the build is signed but not notarized, and the workflow
      says so.
- [ ] Windows: `WIN_CSC_LINK` and `WIN_CSC_KEY_PASSWORD` are set.
- [ ] The `release` environment has a required reviewer and a `v*` tag policy.
      The publish job waits there with the draft complete; do not approve it
      until the matrix below passes.
- [ ] `UPDATE_SIGNING_PRIVATE_KEY` is available to the `validate` job before
      the build. Keeping it repository-scoped is the default; moving it into
      the `release` environment also moves the key check behind the reviewer.
- [ ] The first signed build is rehearsed on the throwaway repo; expect to
      iterate on macOS entitlements and notarization there.
- [ ] On the release candidate, the **Check the update signing key** step
      passes, and `codesign --verify --deep --strict` plus
      `xcrun stapler validate` pass for both `release/mac/APIWeave.app` and
      `release/mac-arm64/APIWeave.app`.
- [ ] On Windows, `Get-AuthenticodeSignature` reports `Valid` for the built
      installer.
- [ ] If a configured certificate cannot be used, stop. Do not publish a
      release note that claims a signature the artifact does not carry.
- [ ] If the release is intentionally unsigned, confirm the release notes and
      installation docs state the SmartScreen/Gatekeeper workaround.

## Post-Release Verification

Only after the tag is pushed and the publish job has completed:

- [ ] `gh release view v1.0.0` shows a published release, not a draft or
      prerelease, and the tag points at the release commit on `main`.
- [ ] The asset set is complete: `*-win-x64.exe`, `*-win-x64.msi`,
      `*-win-x64.zip`; `*-mac-x64.dmg`, `*-mac-arm64.dmg`, `*-mac-x64.zip`,
      `*-mac-arm64.zip`; `*.AppImage`, `*.deb`, `*.rpm`, `*.pacman`;
      `latest.yml`, `latest-linux.yml`, `latest-mac.yml`; `version.json`,
      `SHA256SUMS.txt`, `apiweave-cli-1.0.0.tgz` and `apiweave-cli.tgz`.
- [ ] `sha256sum -c SHA256SUMS.txt` passes after downloading the assets.
- [ ] `version.json` carries `"schema": 1`, `"version": "1.0.0"` and
      `"tag": "v1.0.0"`.
- [ ] Each `latest*.yml` names version `1.0.0`, and its `path` and `sha512`
      match the published file. The per-file `apiweaveSignatures` map covers
      both macOS architectures.
- [ ] `npm install -g ./apiweave-cli.tgz` works on Node.js 22.12;
      `apiweave run --help` prints the documented flags; a sample workspace
      repository runs and exits `0` on success and `1` on a failed test.
- [ ] Download the installers from the public release, not the draft, on at
      least one clean machine per platform; install and launch.
- [ ] An installed `0.22.0` sees `1.0.0` on the platforms that self-update and
      installs it; the notice-only platforms link to the release page.
- [ ] The MCP bridge enables, the token regenerates, and an agent launches (and
      resumes where its CLI supports it).
- [ ] The links from `README.md` and `docs/README.md` to the known limitations
      resolve, and the limitations still describe the shipped build.
- [ ] Record the release URL, checksums, signing result and any known issue.
      Never delete a release to roll it back; use the rollout and prerelease
      levers in [Pulling a bad release back](../reference/release-and-updates.md#pulling-a-bad-release-back).

After every box is checked, the tag can be created and pushed:

```bash
git tag -a v1.0.0 -m "APIWeave 1.0.0"
git push origin v1.0.0
```

## Website

The marketing site lives in the separate `apiweave-cloud` repository. The
`chore/1.0-site` branch prepares it for this release.

- [ ] Review and merge `chore/1.0-site` in `apiweave-cloud`.
- [ ] Leave `DESKTOP_BUILDS_CODE_SIGNED` in `apps/web/lib/release.ts` off
      unless the 1.0.0 artifacts are actually signed and notarized. Turning it
      on changes the Windows/macOS installer copy.
- [ ] After the release is public, confirm the site's hero and download page
      show `1.0.0` from the latest GitHub release, and that the macOS 13+,
      glibc 2.34+, eight-chapter tutorial and CLI install copy are current.
- [ ] The tutorial screenshot still predates 1.0; replace it when a new capture
      is available.
